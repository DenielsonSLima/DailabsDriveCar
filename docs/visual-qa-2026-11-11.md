# QA independente do redesign visual

## Escopo e segurança

Base: `82d5ffd2e5be4d0d69bcd987a13e56f97750e7bf`. Executado localmente, sem sessão de produção, sem credenciais e sem operações no banco remoto. Dados das capturas são fictícios. O harness substitui módulos `.service.ts` antes de resolver dependências; o cliente Supabase é substituído por um stub que lança erro em qualquer acesso. Playwright bloqueia toda requisição fora do servidor HTTP local. O CSS Tailwind é compilado localmente, sem depender do CDN para renderizar testes.

## Build e TypeScript

- Baseline exportado com `git archive` para `/tmp/dailabs-baseline`, sem copiar modificações de trabalho.
- Build baseline: passou com `NODE_OPTIONS=--max-old-space-size=768 npm run build`.
- Build redesign: passou com a mesma configuração.
- `tsc --noEmit`, baseline e redesign: falha com os mesmos 37 diagnósticos (43 linhas de log); comparação dos logs não apresentou diferenças. Incluem referências Deno nas Edge Functions e dependência dotenv ausente em script antigo. Isso não equivale a um typecheck global verde.
- Tentativas iniciais sem limitar heap/concorrentes terminaram por memória; resultados acima vêm das execuções repetidas serializadas.

## Regressões locais existentes

Passaram os 13 scripts existentes: caixa-estoque SQL e UI, estoque-search, lote-cliente-dom, lotes-quantidade SQL e unitário, lotes-resultado, lotes-service, lotes SQL, lotes UI, lotes-values, receivables e venda-lote-integration.

Os scripts SQL usam PGlite local em memória, sem servidor/banco remoto. Os testes DOM de lote exercitam busca por nome/acento/documento, validação, cancelamento/Escape, preservação de campos, erro e retry com UUID estável, bloqueio durante salvamento, atualização do cliente selecionado, conclusão de venda mockada e remoção do modal.

## Paridade estrutural

`node scripts/test-visual-parity.mjs` compara AST TypeScript/TSX e conteúdo SQL de 548 arquivos existentes na base. O relatório JSON fica em `scratch/visual-qa/ast-parity.json`.

A primeira camada remove somente `className`, `style`, `data-drivecar-ui` e `data-drivecar-auth`; preserva handlers, expressões condicionais, imports, textos, rotas, serviço, atributos de formulário e cálculos. A segunda camada é explicitamente classificada como apresentação revisada: atributos ARIA/role, associação de labels e autocomplete de login/senha, oito nomes conhecidos de constantes de classes e o elemento style do preview. Essas exceções não são silenciosamente classificadas como diferença zero. Não há alteração de lógica inexplicada após essas classificações. A inspeção de CSS é visual e não uma prova de equivalência funcional.

## Browser e capturas

Harness: `scripts/test-visual-browser.mjs`. Usa componentes reais de Início, Financeiro/Visão Geral, Cadastros, Relatórios, Ajustes, Cidades, Estoque, Parceiros e Login, envoltos no Layout real (exceto login), além de ConfirmModal, preview de relatório e venda do lote. Viewports: 1440×1000 e 390×844.

As fixtures incluem valores numéricos no dashboard e financeiro; listas de cadastros/estoque/parceiros estão vazias de propósito. O critério de renderização examina conteúdo principal e texto esperado por módulo, não apenas sidebar. O harness registra pageerror, overflow horizontal, foco em botão de modal, remoção ao fechar, Escape no modal de lote e preservação de estilo do documento dentro do preview. Retorna código diferente de zero em pageerror, conteúdo principal ausente ou overflow. Erros nas assertions interrompem a execução.

Relatório: `scratch/visual-qa/browser-report.json`. Capturas PNG no mesmo diretório, nomeadas por módulo e largura. Arquivos gerados e bundles em scratch não devem entrar no commit.

O documento de teste dentro do preview conserva 10px, peso 900 e uppercase. É uma verificação do isolamento de CSS, não uma comparação de PDFs exportados. Não foi acionado download/exportação; a tentativa automática do preview de carregar html2pdf do CDN foi bloqueada pelo harness.

## Reproduzir

As dependências de QA são externas ao package.json do projeto:

```sh
npm ci
npm install --prefix /tmp/dailabs-qa-tools --cache /tmp/npm-cache tailwindcss@3 @electric-sql/pglite
npm install --prefix /tmp/dailabs-browser-legacy --cache /tmp/npm-cache playwright-core@1.51.1
PLAYWRIGHT_BROWSERS_PATH=/tmp/dailabs-browsers node /tmp/dailabs-browser-legacy/node_modules/playwright-core/cli.js install chromium-headless-shell
node scripts/test-lotes-ui.mjs --preview
PLAYWRIGHT_MODULE=/tmp/dailabs-browser-legacy/node_modules/playwright-core/index.mjs CHROMIUM_PATH=/tmp/dailabs-browsers/chromium_headless_shell-1161/chrome-linux/headless_shell node scripts/test-visual-browser.mjs
node scripts/test-visual-parity.mjs
```

Para teste DOM existente, instale happy-dom em diretório de QA e defina HAPPY_DOM_MODULE apontando para `happy-dom/lib/index.js`. Para testes SQL defina PGLITE_MODULE_PATH apontando para `@electric-sql/pglite/dist/index.js`. O Chromium instalado no sistema falhou por restrição de socket de perfil; o headless-shell oficial funcionou sem alterar configurações de segurança do sistema.

## Limites

Não é cobertura funcional de 100%: não valida persistência remota, permissões RLS reais, autenticação real, integração de pagamentos, impressão/download de PDF, fontes remotas, fotos externas, navegadores diferentes, todos os modais ou todos os estados de cada módulo. A QA local preserva a separação entre simulação e produção. Acessibilidade verificada é parcial; não foi feita auditoria WCAG completa nem confirmado focus trap de todos os modais antigos.

## Resultado consolidado

Paridade final: 548 arquivos verificados, 205 idênticos, 343 TSX modificados (329 diferenças somente de atributos visuais e 14 com apresentação/acessibilidade explicitamente revisada); nenhuma diferença funcional inexplicada. O relatório browser final deve conter 24 cenários, zero pageerror, zero conteúdo principal ausente e zero overflow horizontal.

Resultado observado na rodada final serial: 24 cenários browser passaram, sem pageerror, sem ausência de conteúdo principal esperado e sem overflow horizontal nos viewports testados. Foco entrou no modal de venda do lote; Escape removeu o diálogo nas duas larguras. O modal de confirmação aceitou foco no botão Cancelar e foi removido ao cancelar. Essas verificações não garantem focus trap completo.

Capturas de entrega (também com dados fictícios): `entrega-inicio-dados-ficticios.png`, `entrega-financeiro-dados-ficticios.png` e `entrega-lote-modal-dados-ficticios.png` em `scratch/visual-qa/`. O harness oculta somente sua toolbar artificial ao capturar os dois desktops, sem modificar o aplicativo. As demais capturas preservam a identificação explícita do ambiente de testes.

## Ampliação: sidebar escura, ícones e fluxos comerciais/financeiros

Solicitada após a primeira revisão visual. Harness adicional: `scripts/test-visual-workflows.mjs`, com fixtures locais em `scripts/visual-workflows-commercial-fixtures.mjs` e `scripts/visual-workflows-finance-fixtures.mjs`. As fixtures simulam parceiros, veículo, pedidos, pagamentos, títulos, contas e histórico. Não usam dados de clientes reais, sessões, credenciais ou banco remoto. Métodos de mutação dos mocks comerciais/financeiros lançam erro intencional; nenhum botão de gravação, baixa ou faturamento foi submetido.

### Cobertura observada

O catálogo agregado está em `scratch/visual-workflows/report.json`, com 63 capturas/estados únicos. Abrange:

- Início com KPIs, gráfico e veículo fictício; captura completa e viewport desktop 1440×1000.
- Compra/Entrada e Venda/Saída: listagens com dados, abas efetivados/mês atual, rascunhos e todos; detalhes de pedido rascunho e formulários reais de edição pré-preenchidos. Listagem, detalhes e formulário capturados também em 390×844.
- Quatro modais comerciais reais: estruturar pagamento, confirmar entrada, estruturar recebimento e faturar venda, em desktop/mobile. Pagamento/recebimento também em estado preenchido, com valor, PIX, condição e conta de teste. Fechar foi acionado e a remoção do overlay foi confirmada, sem submit.
- Financeiro: todas as 12 abas atuais da configuração com despesas separadas: Dashboard, Contas a Pagar, Contas a Receber, Despesas Variáveis, Despesas Fixas, Outros Créditos, Outros Débitos, Retiradas, Transferências, Histórico Geral, Anotações e Ajustes. As listas usam títulos/movimentações fictícios, não apenas estados vazios.
- Contas a Pagar/Receber: aberto, pagos e todos; detalhe de título a pagar.
- Seis variantes de ModalBaixa: pagar, receber, despesas fixas, variáveis, outros créditos e outros débitos, em desktop/mobile. Cancelar foi acionado e a remoção do modal foi verificada.
- Transferência: lista e formulário Nova Movimentação.
- Em mobile, scroll de baixa a pagar/receber comprovou que o botão Confirmar cabe no viewport após rolar. Capturas adicionais `baixa-contas-pagar-mobile-acoes.png` e `baixa-contas-receber-mobile-acoes.png` registram as ações inferiores. Nenhuma confirmação financeira foi executada.

O harness verifica conteúdo principal, ausência de erros de página, ausência de `NaN`/`Invalid Date` e overflow horizontal global; capturas modais finais verificam origem do overlay em x=0/y=0. O catálogo final não possui erros de página, lacunas de execução, dados inválidos detectados ou overflow horizontal nos estados testados. Isso não é uma medição de cobertura de código nem comprovação de todas as ações do sistema.

### Achados corrigidos somente em apresentação

- `ModalBaixa`: `!m-0` na raiz fixed neutraliza margem herdada de `space-y`, eliminando faixa descoberta no topo.
- A regra central de CSS `[data-drivecar-ui].fixed.inset-0 { margin: 0 !important; }` cobre outros overlays opt-in, inclusive confirmações comerciais. Confirmações foram recapturadas e verificadas.
- `PedidoCompraCard` e `PedidoVendaCard`: valores monetários deixaram de usar truncate; grid passou a duas colunas com total/margem na largura inteira, labels legíveis e números tabulares. Placeholders de foto tiveram contraste corrigido. Handlers, campos, cálculos e textos de negócio foram mantidos.
- Sidebar escura e ícones decorativos neutros foram aplicados conforme a direção posterior; cores com significado de status/alerta foram preservadas.

### Execução e recursos

Para rodar o harness adicional, use as dependências e variáveis PLAYWRIGHT_MODULE/CHROMIUM_PATH documentadas acima. `QA_SCENES` permite selecionar cenas separadas por vírgula; `QA_FINANCE_TABS` seleciona abas financeiras pelos slugs; `QA_APPEND_REPORT=1` agrega cenários recapturados por nome; `QA_SMOKE=1` valida sem gerar PNGs. A execução usa contexto de navegador novo a cada cena/aba para limitar memória. Rodadas longas iniciais sofreram crash de renderer; os cenários afetados foram repetidos em contextos novos e os resultados válidos foram agregados. PNG com pintura incompleta de Receber foi descartado por substituição e reinspecionado.

O relatório geral de 24 cenários da rodada original é repetido no código atualizado e preservado separadamente em `scratch/visual-qa/browser-report-final.json`. Os 13 scripts locais de regressão correspondem à rodada anterior; não houve mudança de lógica de produto nesta extensão. O typecheck anterior registrou 37 erros preexistentes idênticos à base; não foi alegado typecheck verde.

### Limites desta ampliação

Não valida backend, autenticação/RLS de produção, persistência, efetivação de compras/vendas, baixar valores, conciliação real, ações destrutivas, geração de documentos/exportação ou novas integrações. Não cobre todos os modais de cadastro/edição, consignação, todas as combinações de filtros, nem todos os estados de erro/loading. A configuração de despesas unificadas não foi exercitada. O foco foi revisão visual e abertura/fechamento dos fluxos e variantes enumerados, com dados controlados.
